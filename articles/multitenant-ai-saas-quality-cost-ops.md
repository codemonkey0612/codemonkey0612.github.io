マルチテナントのAIエージェントSaaSで、回答品質・速度・コストを両立させる土台は4つに絞れます。評価用データセット、参照元表示、ログ管理、エラー監視です。2024年4月から約2年、7名チームでテックリードを務めた案件の事実に沿って、構成と考え方を整理します。同じ課題に直面した方が、最初に何から手を付けるかを決める材料になれば幸いです。

## 案件の状況

案件は、中堅IT企業向けのAIエージェント・マルチテナントSaaS開発です。期間は2024年4月から2026年7月です。

体制は7名で、PM1名、AIエンジニア2名、バックエンド2名、フロントエンド1名、インフラ1名でした。私はAIエンジニア兼テックリードとして、次を担当しました。

- アーキテクチャ設計
- RAG構築とLLM連携
- API・DB設計
- マルチテナント化
- クラウド構築
- コードレビュー

スタックは Python、FastAPI、Next.js、TypeScript、OpenAI API、PostgreSQL、AWS、Docker です。

課題は明確でした。企業ごとにデータ構造・権限・業務フローが異なります。その状況で情報漏えいを防ぎつつ、AIの回答品質・速度・運用コストを両立する必要がありました。

## 最初に見えていた問題と選択肢

マルチテナントAIでは、品質・速度・コストが互いに引っ張り合います。たとえば検索件数を増やせば品質は上がりやすいですが、トークン量が増えて遅く高くなります。一方で、漏えい防止は他の3つと別格です。起きたら取り返しがつかないからです。

そこで私は、判断の順番を次のように置きました。以下は設計上の考え方です。

- 第一に、安全性（テナント分離と権限）を設計で担保する
- 第二に、品質を測れる状態にする
- 第三に、測った数字をもとに速度とコストを調整する

測れない状態でチューニングを始めると、改善か劣化かの判断ができません。この順番は一般にも有効だと考えています。

## 選んだ構成

実装した要素は、企業単位のデータ分離、ロール別権限、文書のインデックス化とベクトル検索、RAG回答生成、API認証です。

### 分離と権限の考え方

一般論として、分離の単位は検索より前に決めます。検索後に絞り込む設計は、取りこぼしや漏れの原因になりやすいからです。以下は PostgreSQL と FastAPI で同じ考え方を示す、一般的な例です。案件のコードそのものではありません。

```python:search.py
from fastapi import Depends, FastAPI, HTTPException

app = FastAPI()

class Principal:
    def __init__(self, tenant_id: str, role: str):
        self.tenant_id = tenant_id
        self.role = role

async def current_principal() -> Principal:
    # 実際にはトークン検証の結果から生成する
    raise HTTPException(status_code=401)

SQL = """
SELECT id, content
FROM chunks
WHERE tenant_id = %(tenant_id)s
  AND allowed_roles && %(roles)s
ORDER BY embedding <=> %(query_vec)s
LIMIT %(k)s
"""
```

ポイントは3つです。

- テナントIDはリクエスト本文ではなく、認証済みトークン由来の値だけを使う
- ロールの条件を、ベクトル距離の並べ替えより前の WHERE 句に置く
- 件数 k は設定値にして、後で品質とコストの調整に使う

pgvector を使う場合の演算子は、距離の種類で変わります。利用する版の[pgvector公式リポジトリ](https://github.com/pgvector/pgvector)で確認してください。

## 品質を測り続ける土台

ここが記事の中心です。案件では、評価用データセットでの品質検証、回答の参照元表示、ログ管理、エラー監視を整備しました。以降の具体的な手順は、私ならこうする、という助言として書きます。

### 評価用データセット

私なら、質問・期待する根拠文書・期待する回答の要点の3点を1行にした小さなセットから始めます。最初は数十件で十分です。

```python:eval.py
import json

def hit_at_k(retrieved_ids, gold_ids):
    return any(i in gold_ids for i in retrieved_ids)

def run(path, search_fn, k=5):
    hits, total = 0, 0
    with open(path, encoding="utf-8") as f:
        for line in f:
            row = json.loads(line)
            ids = search_fn(row["tenant_id"], row["question"], k)
            hits += hit_at_k(ids, row["gold_doc_ids"])
            total += 1
    return hits / total
```

この例は検索段階の命中率だけを測ります。回答生成の評価は別に用意し、検索と生成を切り分けます。切り分けると、悪化の原因が検索か生成かを特定できます。

テナントごとにデータ構造が違うなら、データセットもテナント別に持つのが筋です。権限の検証用に「見えてはいけない文書を引かないか」というケースも入れます。

### 参照元表示

回答に根拠の文書名や該当箇所を添えると、利用者が自分で検証できます。品質の改善にも効きます。誤りの報告が「どの文書を引いたか」まで特定できるからです。実装上は、生成時に使ったチャンクIDを保持し、レスポンスに含めます。権限のない文書の名前が出ないよう、表示用の情報も検索と同じ絞り込みを通します。

### ログ管理

私なら、1リクエストごとに次を構造化ログで残します。

- リクエストID、テナントID、ロール
- 質問、取得したチャンクID、参照元
- モデル名、入力・出力トークン数
- 各段階の所要時間

トークン数と所要時間を持てば、速度とコストをテナント別に数字で見られます。一方で、質問文や回答には機密が含まれ得ます。保存期間、閲覧権限、マスキングを先に決めます。

```python:logging_setup.py
import json, logging, time

logger = logging.getLogger("rag")

def log_event(request_id, tenant_id, **fields):
    logger.info(json.dumps(
        {"ts": time.time(), "request_id": request_id,
         "tenant_id": tenant_id, **fields},
        ensure_ascii=False))
```

### エラー監視

LLM連携では、タイムアウト、レート制限、空の検索結果、不正な出力形式などが起こります。私なら、これらを種類別に分類して通知します。単に例外を拾うだけでは、品質の低下には気づけません。検索結果ゼロの割合や、参照元なしで返した回答の割合も監視対象にします。

## 結果

複数企業が安全に使えるAI業務基盤を構築しました。社内情報検索と問い合わせ対応の効率化を目的に構築しました。AIエージェントの追加や企業別の機能拡張にも対応できる構成にしました。

## 同じ課題に直面したら最初にやること

私なら、次の順で進めます。

- 分離の単位を決め、テナントIDと権限を検索条件の最初に入れる
- 評価用データセットを数十件で作り、命中率を測る
- 回答に参照元を付け、権限の絞り込みを通す
- リクエスト単位の構造化ログにトークン数と所要時間を含める
- エラーの種類を分け、検索結果ゼロなど品質の兆候も監視する
- その後で、k やモデルを変えて速度とコストを調整する

### 落とし穴

- 検索後にテナントで絞ると、漏れや取りこぼしにつながる
- ログに機密を無制限に残してしまう
- 評価セットを作らずに、感覚でプロンプトを直し続ける
- 検索と生成の評価を混ぜて、原因が分からなくなる

## まとめ

マルチテナントAIの土台は、評価用データセット、参照元表示、ログ管理、エラー監視の4つです。まず安全性を設計で固め、品質を測れるようにし、その数字で速度とコストを調整するのが近道だと考えています。
