## 始まりの状況：資料が複数の場所にばらばらの形式で保存されていた

案件の概要は次のとおりです。

- 期間：2019年5月〜2020年3月
- 体制：5名（PM1・エンジニア2・業務担当2）
- 私の担当：バックエンドエンジニアとして、検索基盤設計、文書取り込み、全文検索API、DB設計、権限管理
- 技術スタック：Python、Django、PostgreSQL、Elasticsearch、JavaScript、REST API

課題は、資料が複数の場所にばらばらの形式で保存されていて、必要な情報を探すのに時間がかかることでした。探す人は、置き場所を一つずつ開いて確認するしかありません。わからなければ担当者に聞くことになります。

この状態を「検索エンジンを入れれば解決」と捉えると失敗しやすいと、私は考えています。検索の速さ以前に、次の3つが決まっていないと、検索結果の質も安全性も保てないからです。

- 何をどうやって検索対象に入れるか
- 誰に何を見せるか
- どんな条件で絞り込み、どう並べるか

以降は、この3つを順に説明します。

## 最初に決めたこと1：文書の自動取り込みとテキスト抽出

### 手作業の登録をやめる

最初に決めたのは、文書の取り込みを自動化し、テキスト抽出まで同じ流れに乗せることです。手作業での登録に頼ると、更新が止まった時点で検索結果が古くなり、誰も使わなくなります。

設計の一般的な例として、置き場所ごとの差を吸収する層を作り、そこから共通の形式でElasticsearchに登録する構成が考えられます。私ならこの層を、次のように分けます。

- コネクタ：各保存場所から、ファイルと更新日時を取得する
- 抽出器：形式ごとにテキストを取り出す
- 登録処理：共通のドキュメント形式に整えてインデックスへ入れる

### 共通ドキュメントの形を決める

場所や形式が違っても、検索側から見えるドキュメントは同じ形にします。ここで元の場所を示すIDを持たせておくと、再取り込み時に上書きでき、重複を避けられます。

```python:ingest.py
import hashlib
from datetime import datetime, timezone
from elasticsearch import Elasticsearch

es = Elasticsearch("http://localhost:9200")  # 例：ローカル検証用
INDEX = "documents"


def extract_text(path: str) -> str:
    """形式ごとの抽出処理を呼び分ける（実装は形式ごとに用意する）。"""
    raise NotImplementedError


def make_doc_id(source: str, source_path: str) -> str:
    # 保存場所＋パスから決定的なIDを作る。再取り込みで上書きされる。
    return hashlib.sha256(f"{source}:{source_path}".encode()).hexdigest()


def ingest(source: str, source_path: str, title: str,
           category: str, allowed_groups: list[str], modified_at: datetime):
    body = extract_text(source_path)
    es.index(
        index=INDEX,
        id=make_doc_id(source, source_path),
        document={
            "title": title,
            "body": body,
            "category": category,
            "source": source,
            "source_path": source_path,
            "allowed_groups": allowed_groups,
            "modified_at": modified_at.astimezone(timezone.utc).isoformat(),
        },
    )
```

ポイントは `id` を決定的に作ることです。同じ文書を何度取り込んでも、1件に収まります。定期実行にしても、件数が膨れません。

### 抽出失敗を前提にする

テキスト抽出は必ず失敗するものが出ます。スキャン画像だけのPDFや、壊れたファイルがその例です。私なら、失敗した文書を黙って捨てず、失敗一覧として残します。検索に出てこない理由を説明できないと、利用者の信頼を失うためです。

## 最初に決めたこと2：閲覧権限を検索の仕組みに組み込む

### 後付けにしない

2つ目は、閲覧権限を検索の仕組みの中に最初から組み込むことです。社内の文書には、全員が見てよいものと、部署限定のものが混ざります。検索結果を出してから画面側で隠す方式は、件数や候補表示から内容が漏れやすいので、私は勧めません。

一般に、権限は次の考え方で設計できます。

- 各ドキュメントに、閲覧を許可するグループのリストを持たせる
- 検索時に、ログインユーザーの所属グループを取得する
- 検索クエリの `filter` で、許可グループと一致する文書だけに絞る

権限判定を検索クエリの内側に入れるので、ヒット件数や集計にも権限が反映されます。

### 検索側のコード

```python:search.py
from elasticsearch import Elasticsearch

es = Elasticsearch("http://localhost:9200")


def search(keyword: str, user_groups: list[str],
           category: str | None = None, size: int = 20):
    filters = [{"terms": {"allowed_groups": user_groups}}]
    if category:
        filters.append({"term": {"category": category}})

    return es.search(
        index="documents",
        query={
            "bool": {
                "must": [{
                    "multi_match": {
                        "query": keyword,
                        "fields": ["title^3", "body"],
                    }
                }],
                "filter": filters,
            }
        },
        size=size,
        source_excludes=["body"],  # 本文は返さず、通信量を抑える
    )
```

`user_groups` は、必ずサーバー側で認証情報から決めます。クライアントから受け取った値をそのまま使うと、権限が意味を失います。全社公開の文書には、たとえば `"all"` のような共通グループ名を入れておき、全員の所属グループに `"all"` を足す運用にすると単純です。

### 権限変更の反映をどうするか

文書側の権限が変わったとき、インデックスにどう反映するかも決めておく必要があります。私なら、取り込みの定期実行で権限も毎回上書きします。変更の即時性が必要なら、変更イベントで該当文書だけ部分更新する形に広げます。どちらを選ぶにしても、「反映までの遅れ」を業務側と合意しておくことが大切です。

## 最初に決めたこと3：カテゴリ・キーワード検索と、検索条件・データ構造の最適化

### 絞り込みと全文検索を分ける

3つ目は、カテゴリによる絞り込みとキーワード検索を組み合わせ、検索条件とデータ構造を最適化することです。案件では、カテゴリ・キーワード検索を実装し、検索条件とデータ構造を最適化しました。

ここでの私の基本方針は、役割でフィールドの型を分けることです。

- 完全一致で絞るもの（カテゴリ、保存場所、権限グループ）は `keyword` 型にして `filter` で使う
- 文字列として検索するもの（タイトル、本文）は `text` 型にして日本語解析を付ける
- 並べ替えや期間指定に使うもの（更新日時）は `date` 型にする

`filter` はスコア計算に関与しないので、条件が増えても関連度の判断を邪魔しません。

### マッピングの例

```json:mapping.json
{
  "settings": {
    "analysis": {
      "analyzer": {
        "ja_analyzer": {
          "type": "custom",
          "tokenizer": "kuromoji_tokenizer",
          "filter": ["kuromoji_baseform", "lowercase"]
        }
      }
    }
  },
  "mappings": {
    "properties": {
      "title": {"type": "text", "analyzer": "ja_analyzer"},
      "body": {"type": "text", "analyzer": "ja_analyzer"},
      "category": {"type": "keyword"},
      "source": {"type": "keyword"},
      "source_path": {"type": "keyword"},
      "allowed_groups": {"type": "keyword"},
      "modified_at": {"type": "date"}
    }
  }
}
```

この設定を使うには、日本語解析プラグイン（`analysis-kuromoji`）をElasticsearchに入れておく必要があります。作成は次のようにします。

```python:create_index.py
import json
from elasticsearch import Elasticsearch

es = Elasticsearch("http://localhost:9200")
with open("mapping.json", encoding="utf-8") as f:
    conf = json.load(f)

es.indices.create(
    index="documents",
    settings=conf["settings"],
    mappings=conf["mappings"],
)
```

### データ構造で効くこと

データ構造の最適化として、私なら次の点を確認します。

- 本文のような大きなフィールドは、検索結果では返さない（上の `source_excludes`）
- 本文を丸ごと1フィールドに入れず、長い文書は章やページ単位に分けるかを検討する
- 業務で使わない項目はインデックスに入れない
- 同義語や表記ゆれは、実際の検索ログを見てから辞書に足す

特に表記ゆれは、先に辞書を作り込むより、よく使われる検索語と「ヒットしなかった語」を見て足すほうが、効果が確かめやすいと考えます。

## 結果：検索時間約60%削減と、担当者への問い合わせ減少

この案件の結果は、社内情報の検索時間を約60%（測定方法は非公開）削減し、担当者への問い合わせを減らせたことです。

私がこの結果から言えるのは、次の点までです。

- 探す場所が1つになり、形式の違いを利用者が意識しなくてよくなった
- カテゴリとキーワードで絞れるので、候補を順に開く作業が減った

## 同じ課題に直面したら最初にやること（たとえばの確認手順）

ここからは、私ならこうするという手順です。実際の案件の経過ではありません。

### 手順1：現状の探し方を数える

たとえば、資料が共有フォルダ、メール添付、業務システムの3か所にあるとします。最初に、よく探される資料の上位を10件ほど挙げてもらいます。それぞれについて、置き場所、形式、閲覧できる範囲をメモします。この表がそのまま、取り込みと権限の設計の入力になります。

### 手順2：権限モデルを先に決める

次に、グループの単位を決めます。部署単位なのか、プロジェクト単位なのかです。既存の認証基盤のグループと対応づけられるかも確認します。ここが曖昧なまま作り始めると、後から作り直しになりやすいです。

### 手順3：小さく取り込んで検索してみる

1か所の置き場所と、2つの形式だけで取り込みを動かします。先ほどの `ingest` と `search` で十分に試せます。業務担当の方に、実際に探している語で検索してもらい、ヒットしない原因を記録します。

### 手順4：確認のチェックリスト

- 同じ文書を2回取り込んでも、件数が増えないか
- 抽出に失敗した文書の一覧が見られるか
- 権限のないユーザーで検索して、タイトルも件数も出ないか
- カテゴリの絞り込みを外すと、件数が増えるか
- 検索結果で本文を返していないか
- 権限変更の反映にかかる時間を、業務側が了承しているか

### よくある落とし穴

- 権限を画面側の表示制御だけで済ませる
- 抽出できなかった文書を、気づかないまま検索対象外にする
- すべてを `text` 型にして、絞り込みの精度と速度を落とす
- 検索ログを取らず、改善の根拠がなくなる

## まとめ

社内検索を全文検索基盤にする際、私が最初に決めるのは次の3つです。

- 取り込みを自動化し、抽出失敗も含めて追えるようにする
- 閲覧権限を検索クエリの内側に組み込む
- 絞り込み用と検索用でフィールドの型を分け、検索条件とデータ構造を整える

この順で進めた案件では、検索時間を約60%（測定方法は非公開）削減し、担当者への問い合わせも減らせました。検索エンジンの選定より前に、この3点を決めておくことが近道だと考えています。
