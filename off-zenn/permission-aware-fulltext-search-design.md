社内文書検索の案件で、私は社内情報の検索時間を約60%削減し、担当者への問い合わせも減らしました。この記事では、その案件を材料に、取り込み・テキスト抽出・インデックス・閲覧権限の4点について、着手前に決めておきたいことを整理します。社内検索やナレッジ管理を作る予定のエンジニアに向けた内容です。

なお、案件の事実として書くのは、期間・体制・役割・実装した機能・結果までです。それ以外の部分は「私ならこうします」という一般論や設計案として書き、区別できるようにしています。

## 案件の始まり：資料が複数の場所にばらばらの形式で保存されていた

案件は、中堅企業向けの社内文書検索・ナレッジ管理システムの開発です。期間は2019年5月から2020年3月で、体制は5名（PM1名、エンジニア2名、業務担当2名）でした。

私の役割はバックエンドエンジニアで、検索基盤の設計、文書取り込み、全文検索API、DB設計、権限管理を担当しました。技術スタックは Python、Django、PostgreSQL、Elasticsearch、JavaScript、REST API です。

課題は、資料が複数の場所にばらばらの形式で保存されていて、必要な情報を探すのに時間がかかることでした。実装したのは次の5点です。

- 文書の自動取り込み
- テキスト抽出
- 全文検索インデックス
- カテゴリ・キーワード検索
- 閲覧権限

あわせて、検索条件とデータ構造を最適化しました。以降は、この5点を「先に決めたい4つのこと」に束ねて説明します。

## 最初に決めたいこと1：取り込みの対象と自動化の範囲

検索システムの品質は、何が入っているかでほぼ決まります。実装より先に、次の3点を決めたいです。

- どの保存場所を対象にするか
- どの形式まで対応するか
- どこまでを自動化し、どこを手作業に残すか

私なら、最初に対象の保存場所と形式を棚卸しして、件数の多い順に並べます。全部を一度に対応しようとすると、取り込みの例外処理で時間が尽きるためです。

### 取り込みの設計メモ

取り込み処理は、次の形に分けておくと後で楽です。以下は一般的な設計案です。

- 収集：保存場所ごとのコネクタが、ファイルとメタデータを取得する
- 識別：元の場所のパスや ID から、安定した文書 ID を作る
- 差分：更新日時やハッシュで、変更があった文書だけを再処理する
- 失敗の記録：抽出に失敗した文書は捨てずに、理由つきで残す

特に、文書 ID を元の場所から決められる形にしておくことを勧めます。再取り込みのたびに重複が増えるのを防げるからです。

```python:ingest/identity.py
import hashlib


def document_id(source: str, path: str) -> str:
    """保存場所名とパスから、再取り込みしても変わらない ID を作る。"""
    raw = f"{source}:{path}".encode("utf-8")
    return hashlib.sha256(raw).hexdigest()


def content_hash(data: bytes) -> str:
    """本文が変わったかどうかの判定に使う。"""
    return hashlib.sha256(data).hexdigest()
```

`document_id` は同じ文書に対して常に同じ値を返します。これを Elasticsearch の `_id` に使えば、再取り込みは上書きになります。`content_hash` を DB に保存しておけば、変更のない文書の抽出をスキップできます。

### 自動化の範囲で迷ったら

削除の扱いは、先に決めておきたい項目です。元の保存場所から消えた文書を、検索結果からも消すのかどうかです。権限のある情報が消えずに残ると、事故につながります。私なら、削除は検索から即時に外す方針にします。

## 最初に決めたいこと2：テキスト抽出と全文検索インデックスの設計

形式がばらばらな資料から、まず本文を取り出す必要があります。ここで決めるのは、抽出の担当と、インデックスに入れる項目です。

### テキスト抽出

一般に、PDF、Office 文書、プレーンテキストでは抽出の難しさが大きく違います。スキャンした画像だけの PDF には、そもそも文字がありません。OCR を入れるかどうかは、費用と精度に直結するので、着手前に業務担当と合意しておきます。

私なら、抽出処理は「バイト列を受け取り、テキストと状態を返す」関数に統一します。形式ごとの差を、その内側に閉じ込めるためです。

```python:ingest/extract.py
from dataclasses import dataclass
from pathlib import Path


@dataclass
class Extracted:
    text: str
    ok: bool
    reason: str = ""


def extract_text(path: Path) -> Extracted:
    suffix = path.suffix.lower()
    try:
        if suffix in {".txt", ".md"}:
            return Extracted(path.read_text(encoding="utf-8"), True)
        # PDF や Office 形式は、形式ごとの抽出関数をここに追加する
        return Extracted("", False, f"unsupported: {suffix}")
    except Exception as e:  # 失敗した文書も理由つきで残す
        return Extracted("", False, repr(e))
```

対応しない形式は `ok=False` と理由を返します。この結果を一覧にすると、どの形式の対応を増やすべきかが数字で見えます。

### インデックスの設計

全文検索では、日本語の分かち書きが検索の質を左右します。Elasticsearch で日本語を扱うなら、形態素解析の kuromoji プラグインを使う構成が一般的です。プラグインの導入が必要なので、運用環境で入れられるかも先に確認します。

```json:mapping.json
{
  "settings": {
    "analysis": {
      "analyzer": {
        "ja": {
          "type": "custom",
          "tokenizer": "kuromoji_tokenizer",
          "filter": ["kuromoji_baseform", "lowercase"]
        }
      }
    }
  },
  "mappings": {
    "properties": {
      "title":          {"type": "text", "analyzer": "ja"},
      "body":           {"type": "text", "analyzer": "ja"},
      "category":       {"type": "keyword"},
      "source":         {"type": "keyword"},
      "updated_at":     {"type": "date"},
      "allowed_groups": {"type": "keyword"}
    }
  }
}
```

ポイントは次のとおりです。

- `title` と `body` は分かち書きして全文検索の対象にする
- `category` と `source` は `keyword` にして、絞り込みと集計に使う
- `allowed_groups` は閲覧できるグループの一覧で、後述の権限制御に使う

本文の全体を1つの項目に入れるか、章ごとに分けるかも決めどころです。長い文書は、分けるとヒット箇所を示しやすくなります。一方で文書数が増えます。私なら、まず文書単位で始めて、必要が出てから分割します。

## 最初に決めたいこと3：カテゴリ・キーワード検索と閲覧権限の持たせ方

案件では、カテゴリ・キーワード検索と閲覧権限を実装しました。ここでは、その設計で迷いやすい点を一般論として書きます。

### カテゴリは絞り込み、キーワードは順位づけ

カテゴリは、`filter` に入れるのが基本です。スコアに影響せず、結果をキャッシュしやすいからです。キーワードは `must` に入れて、関連度で並べます。

### 権限は検索の内側で絞る

最も避けたいのは、検索した後で権限のない文書を取り除く方式です。件数やページ送りがずれますし、取り除き忘れのリスクもあります。私なら、権限の条件をクエリの `filter` に必ず入れます。

```python:search/query.py
from elasticsearch import Elasticsearch

es = Elasticsearch("http://localhost:9200")  # 例：ローカル環境


def search(keyword: str, user_groups: list[str], category: str | None = None):
    filters = [
        # 公開文書か、ユーザーの所属グループが許可された文書だけを対象にする
        {"terms": {"allowed_groups": user_groups + ["public"]}}
    ]
    if category:
        filters.append({"term": {"category": category}})

    return es.search(
        index="documents",
        query={
            "bool": {
                "must": [
                    {
                        "multi_match": {
                            "query": keyword,
                            "fields": ["title^3", "body"],
                        }
                    }
                ],
                "filter": filters,
            }
        },
        size=20,
    )
```

`user_groups` は、リクエストを送ったユーザーの所属から、サーバー側で決めます。クライアントから受け取った値をそのまま使ってはいけません。`title^3` は、タイトルの一致を本文より重く見る指定です。

### 権限の正本は DB に置く

権限の元データは、Django と PostgreSQL 側に置くのが扱いやすいです。Elasticsearch の `allowed_groups` は、そこから作る写しと考えます。

```python:documents/models.py
from django.db import models


class Document(models.Model):
    doc_id = models.CharField(max_length=64, unique=True)
    title = models.CharField(max_length=500)
    category = models.CharField(max_length=100, db_index=True)
    source = models.CharField(max_length=100)
    content_hash = models.CharField(max_length=64)
    updated_at = models.DateTimeField()


class DocumentAccess(models.Model):
    document = models.ForeignKey(
        Document, on_delete=models.CASCADE, related_name="accesses"
    )
    group = models.CharField(max_length=100, db_index=True)
```

ここで決めておくべきなのは、権限が変わったときの反映方法です。文書本体が変わらなくても、権限の変更だけでインデックスの更新が必要になります。権限変更を検知して、該当文書の `allowed_groups` だけを部分更新する経路を用意します。

もう1つ、権限の元をどこにするかも重要です。元の保存場所の権限を引き継ぐのか、検索システム側で独自に持つのか。前者は正確ですが、連携が重くなります。後者は単純ですが、二重管理になります。どちらかを、着手前に業務担当と決めます。

## 最初に決めたいこと4：検索条件とデータ構造の最適化をどう測るか

案件では、検索条件とデータ構造を最適化しました。最適化は、測れなければ終わりません。そこで、測り方を先に決めておくことを勧めます。

### 測るものを3つに絞る

私なら、次の3つから始めます。以下は一般的な指標の案です。

- 探す時間：業務担当に依頼して、代表的な探し物を数件選び、導入前後で所要時間を比べる
- 見つかった率：同じ探し物で、目的の文書が上位に出たかを記録する
- 担当者への問い合わせ数：「あの資料はどこ」という質問の件数

探し物のセットは、最初に固定します。後から変えると、前後比較ができなくなります。

### 検索ログを残す

検索語、絞り込み条件、ヒット件数、クリックされた文書を記録します。ヒット0件の検索語は、同義語や表記ゆれの辞書を直す手がかりになります。

### 最適化の観点

一般に、見直す対象は次の3つです。

- 重み：タイトル、本文、カテゴリのどれを重く見るか
- 絞り込み：よく使う条件を `keyword` にして `filter` に出しているか
- データ構造：インデックスに持つ項目と、DB に持つ項目の分担は適切か

変更は1回に1つだけにして、固定した探し物のセットで結果を比べます。複数を同時に変えると、効いた理由が分かりません。

## 結果：検索時間を約60%削減、問い合わせも減った

この案件では、社内情報の検索時間を約60%削減し、担当者への問い合わせを減らすことができました。私なら、資料を1つの検索で横断できるようにすることが効果の土台になると考えます。

一般論として、取り込みから権限までを一続きで設計することが成果につながると考えます。取り込めていない資料は検索できません。抽出できていない本文は、ヒットしません。権限が不安なら、公開範囲を狭めざるを得ません。4つのどれが欠けても、検索の価値は下がります。

## 同じ課題に直面したら、まずやること

最初の1〜2週間で、私なら次の順で進めます。

- 保存場所と形式を棚卸しして、件数の多い順に並べる
- 取り込み対象の最初の範囲と、削除の扱いを決める
- 抽出できない形式を一覧にし、OCR などの要否を合意する
- インデックスの項目を決め、日本語の分かち書きが使えるか確認する
- 権限の正本をどこに置くか決め、変更の反映経路を設計する
- 探し物のセットと測る指標を固定する

### 落とし穴

- 検索後に権限で絞る方式にしてしまい、件数やページ送りがずれる
- 抽出失敗を握りつぶして、検索に出ない文書に誰も気づかない
- 権限だけが変わった文書のインデックスが更新されない
- 探し物のセットを後から変えて、改善が測れなくなる

## まとめ

権限つき全文検索では、取り込みの範囲、テキスト抽出とインデックス、検索と権限の持たせ方、最適化の測り方の4つを、着手前に決めておくと手戻りが減ります。特に権限は、検索の内側で絞ることと、変更の反映経路を用意することが要点です。ご自身の環境に合わせて、まず棚卸しから始めてみてください。
