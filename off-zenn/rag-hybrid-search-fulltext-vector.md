RAGの検索をベクトル検索だけで組むと、型番・固有名詞・略語を含む質問で外れやすくなります。私の立場は「社内文書が対象なら、全文検索を併用する前提で設計し、評価用質問で効果を数字にして判断する」です。この記事は、RAGの検索精度に悩むエンジニアと、併用すべきか迷っている方に向けて書いています。統合手法のRRF（Reciprocal Rank Fusion）をPythonで実装し、Recall@5やMRRで測る方法まで示します。

## ベクトル検索だけで外れやすい質問のパターン

ベクトル検索は「意味の近さ」で文書を探します。言い換えや曖昧な質問には強い一方で、文字列そのものが手がかりになる質問は苦手になりがちです。一般に、次の3パターンで外れやすくなります。

- 型番・品番・エラーコード（例：「ABC-1234」と「ABC-1243」は意味上ほぼ同じに見える）。
- 固有名詞（社内システム名、取引先名、プロジェクト名）。
- 略語・社内用語（正式名称と略称が文書内で混在している）。

たとえば「ABC-1234の交換手順は？」と聞いたとします。ベクトル検索は「交換手順」という意味に引っ張られ、型番違いの手順書を上位に出すことがあります。全文検索なら、型番の文字列が一致する文書を確実に拾えます。

逆に、全文検索だけでは「退職するときの手続き」と「退社時の申請フロー」のような言い換えを拾えません。だから両者は競合ではなく補完の関係だと考えています。

## 全文検索の案件で学んだこと

私は2019年から2020年にかけて、中堅企業向けの社内文書検索・ナレッジ管理システムを開発しました。チームは5名で、私はバックエンドエンジニアとして検索基盤設計、文書取り込み、全文検索API、DB設計、権限管理を担当しました。資料が複数の場所にばらばらの形式で保存され、探すのに時間がかかっていたのが課題です。

文書の自動取り込み、テキスト抽出、全文検索インデックス、カテゴリ・キーワード検索、閲覧権限を実装し、検索条件とデータ構造を最適化しました。スタックはPython、Django、PostgreSQL、Elasticsearchです。結果として、社内情報の検索時間を約60%削減し、担当者への問い合わせも減りました。

この案件が教えてくれたのは、社内の検索では「キーワードで確実に当たる」ことの価値が大きい、という点です。後述の考え方は、この経験とその後のRAG案件を踏まえた、私ならこうするという意見です。

その後のRAG案件（文書解析システム、マルチテナントSaaS）では、ベクトル検索を使った検索と、評価用の質問データでの品質検証に取り組みました。評価用質問で検索精度を測り、改善を繰り返す進め方は、併用の判断にもそのまま使えます。

## 併用するか迷ったときの判断基準

私なら、次の項目で判断します。2つ以上当てはまれば併用を前提にします。

- 文書に型番・コード・固有名詞が多い。
- 利用者が略語や社内用語で質問する。
- 「その文字列が入った文書を出してほしい」という期待がある。
- 参照元の根拠を人が確認する運用である。
- 評価用質問で、ベクトルのみの場合に失敗した質問の多くが文字列一致で救えそうだ。

当てはまる項目が少なく、文書が一般的な説明文中心なら、まずベクトル検索だけで始めても構いません。ただし、併用の追加コストは小さいです。PostgreSQLを使っているなら、同じDBで全文検索とベクトル検索を両方持てる構成も選べます。日本語の全文検索は、形態素解析やn-gramの設定が品質を左右します。ここは事前に小さく試すことを勧めます。

判断の最終基準は「評価用質問で数字が上がるか」です。感覚で決めず、後述の指標で比べます。

## RRFで2つの検索結果を統合するPythonコード

全文検索のスコアとベクトル類似度は、尺度がまったく違います。単純に足すと、片方に偏ります。そこでRRFを使います。RRFはスコアを使わず、順位だけで複数の検索結果を統合する手法です。

各文書のスコアは、各検索結果での順位に定数を足した値の逆数を、検索結果ごとに合計したものです。コードでは定数の既定値を60にしています。この値は調整できます。

```python:rrf.py
from collections import defaultdict
from typing import Sequence


def rrf_merge(
    rankings: Sequence[Sequence[str]],
    k: int = 60,
    weights: Sequence[float] | None = None,
    top_n: int = 10,
) -> list[tuple[str, float]]:
    """複数の順位リスト(文書IDの列)をRRFで統合する。"""
    if weights is None:
        weights = [1.0] * len(rankings)
    if len(weights) != len(rankings):
        raise ValueError("weights と rankings の長さが違います")

    scores: dict[str, float] = defaultdict(float)
    for ranking, w in zip(rankings, weights):
        seen: set[str] = set()
        for rank, doc_id in enumerate(ranking, start=1):
            if doc_id in seen:  # 同一リスト内の重複は最初だけ数える
                continue
            seen.add(doc_id)
            scores[doc_id] += w / (k + rank)

    merged = sorted(scores.items(), key=lambda x: (-x[1], x[0]))
    return merged[:top_n]


if __name__ == "__main__":
    fulltext = ["doc_a", "doc_c", "doc_d"]   # 全文検索の上位
    vector = ["doc_b", "doc_a", "doc_e"]     # ベクトル検索の上位
    for doc_id, score in rrf_merge([fulltext, vector]):
        print(doc_id, round(score, 5))
```

ポイントは次のとおりです。

- 入力は文書IDの順位リストだけで、検索エンジンの種類に依存する部分がありません。
- 両方で上位に出たdoc_aが最上位になり、片方だけの文書も順位が高ければ残ります。
- 同点時はIDで並べ、結果を毎回同じにします。評価の再現性のために大切です。
- weightsで全文検索側を重くするなどの調整ができます。ただし、まずは等重みで始め、評価用質問で必要性を確認してから触ります。

文書単位ではなくチャンク単位で検索している場合は、チャンクIDで統合してから文書に集約するか、文書IDに集約してから統合するかを決めます。どちらが良いかも、評価用質問で比べるのが確実です。

## 評価用質問セットで併用の効果を測る

併用の是非は、評価用の質問セットで決めます。私なら、次の形で作ります。

- 実際の利用者が聞きそうな質問を、数十件から用意する。
- 各質問に「正解となる文書ID」を1件以上ひも付ける。
- 型番・固有名詞・略語を含む質問と、言い換え中心の質問を両方入れる。

質問を種類別にラベル付けしておくと、どのタイプで効果が出たかが分かります。作成は手間ですが、後の改善すべてで使い回せます。

### Recall@5 と MRR

- Recall@5：上位5件に正解が1件でも入った質問の割合です。Recall@10なら上位10件で数えます。
- MRR：最初に正解が出た順位の逆数を、質問ごとに求めた平均です。

```python:evaluate.py
from typing import Callable, Sequence

Retriever = Callable[[str], list[str]]  # 質問 -> 文書IDの順位リスト


def recall_at_k(results: Sequence[list[str]], golds: Sequence[set[str]], k: int) -> float:
    hits = sum(1 for r, g in zip(results, golds) if g & set(r[:k]))
    return hits / len(golds)


def mrr(results: Sequence[list[str]], golds: Sequence[set[str]]) -> float:
    total = 0.0
    for r, g in zip(results, golds):
        for rank, doc_id in enumerate(r, start=1):
            if doc_id in g:
                total += 1.0 / rank
                break
    return total / len(golds)


def evaluate(name: str, retriever: Retriever, questions: Sequence[str],
             golds: Sequence[set[str]]) -> None:
    results = [retriever(q) for q in questions]
    print(
        f"{name}: Recall@5={recall_at_k(results, golds, 5):.3f} "
        f"Recall@10={recall_at_k(results, golds, 10):.3f} "
        f"MRR={mrr(results, golds):.3f}"
    )
```

使い方は単純です。ベクトルのみ、全文のみ、RRF併用の3つのretrieverを同じ質問セットに通し、`evaluate` で並べます。

```python
evaluate("vector", vector_search, questions, golds)
evaluate("fulltext", fulltext_search, questions, golds)
evaluate("hybrid", lambda q: [d for d, _ in rrf_merge([fulltext_search(q), vector_search(q)])],
         questions, golds)
```

ここで `vector_search` と `fulltext_search` は、質問文字列を受け取り文書IDのリストを返す、ご自身の検索関数です。

### 結果の読み方

- 併用でRecall@5やRecall@10が上がり、MRRも下がらなければ採用です。
- 全体の数字が横ばいでも、型番・固有名詞系の質問だけ上がっているなら、併用の価値はあります。種類別に集計して確認します。
- 言い換え系の質問が悪化していたら、重みや定数を見直します。

質問数が少ないと、1件の違いで数字が大きく動きます。数字は絶対値より、同じ質問セットでの比較として読むのが安全です。

## 本番で私ならこうする：権限フィルタと運用上の落とし穴

### 権限フィルタは検索の段階で掛ける

最も重要なのは権限です。回答生成の後で隠すのではなく、検索の時点で閲覧可能な文書だけを対象にします。全文検索とベクトル検索の両方に、同じ権限条件を渡します。片方だけ漏れていると、RRFで統合した結果に閲覧不可の文書が混ざります。

マルチテナントの案件では、企業単位のデータ分離とロール別権限が前提でした。併用検索でも、テナントIDとロールの条件は両方の検索経路に必ず入れる、というのが私の方針です。統合後の結果に権限チェックをもう一度掛ける二重化も、私なら入れます。

### 運用上の落とし穴

- インデックスの同期ずれ：文書を更新したとき、全文検索側とベクトル側の片方だけ更新されることがあります。更新・削除を同じ処理で扱い、定期的に件数を突き合わせます。
- 日本語の分かち書き設定：辞書や分割方式で、略語や型番が分断されることがあります。評価用質問に、実際の型番を入れておきます。
- 候補数の不足：RRFに渡す各検索の上位件数が少ないと、統合の意味が薄れます。評価で候補数も比べます。
- 評価セットの陳腐化：文書や用語が変わるので、定期的に質問を追加します。本番で外れた質問は、そのまま評価用に足します。
- 参照元の表示：どちらの検索で拾ったかをログに残しておくと、外れた原因を追いやすくなります。

:::message
併用の判断は、文書の性質と利用者の質問の癖で変わります。一般論より、自社の評価用質問での比較結果を優先してください。
:::

## まとめ

- 型番・固有名詞・略語はベクトル検索だけだと外れやすく、全文検索が補います。
- 判断は、文書の性質と評価用質問での数字の両方で行います。
- 統合はRRFが手軽で、検索エンジンの種類に依存しません。
- Recall@5やMRRを、質問の種類別に見て効果を確かめます。
- 本番では、権限条件を両方の検索経路に入れ、インデックス同期を監視します。
