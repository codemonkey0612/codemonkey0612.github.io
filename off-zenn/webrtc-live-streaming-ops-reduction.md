教育・研修事業者向けのライブ配信基盤を開発し、配信準備から参加者管理までの運営作業時間を約50%削減しました。この記事では、その案件（2020年6月〜2021年1月）をふまえ、同じ課題に直面した人が最初に決めたい4つの分割と、最初にやることをまとめます。WebRTCで配信基盤を作ろうとしているエンジニアや、運営の手作業を減らしたい方に向けた内容です。

なお、案件の事実として書くのは、期間・体制・担当範囲・課題・実施内容・結果までです。4つの分割やコード、設計の理由づけは、案件で実際に決めたことではありません。一般的な考え方と「私ならこうする」という助言として書いています。また、約50%削減が4つの分割の効果だとは、この記事では述べていません。

## 案件の状況：端末も回線もバラバラな受講者と、手作業の多い運営

案件は、教育・研修事業者向けのライブ動画配信プラットフォームの開発でした。体制は5名で、PM1名、エンジニア2名、配信担当2名です。私はフルスタックエンジニアとして、次の範囲を担当しました。

- システム設計
- 会員管理
- 配信画面
- 動画処理
- API開発
- AWS構築
- テスト

技術スタックは React、Node.js、WebRTC、WebSocket、FFmpeg、AWS、MySQL です。

課題は2つありました。1つ目は、端末や通信環境によって視聴品質がばらつくことです。2つ目は、その中で安定した配信と簡単な参加手続きを両立することです。受講者側の環境は選べないため、品質は基盤側で吸収する前提になります。

## 最初の課題整理：視聴品質と参加手続きの簡単さをどう両立するか

この2つは、放っておくとトレードオフになります。品質を上げようとすると事前のテストやアプリ導入が増え、参加手続きが重くなります。逆に手続きを軽くしすぎると、環境ごとの不具合が運営への問い合わせとして跳ね返ります。

私ならまず、次の3点を分けて考えます。

- 参加者に求める操作は何か（URLを開く、ログインする、など）
- 品質の劣化を誰が検知し、誰が対応するか
- 配信後にやる作業は何か（録画の確認、変換、公開）

運営作業の削減は、この3点のうち「人が手でやっていること」を機械に寄せることで進みます。そのため設計の最初に、手作業の洗い出しを置くのがよいと考えています。

## 構成の考え方：WebRTC配信・参加者認証・録画管理・動画変換を分ける

実装した範囲は、WebRTCによる配信、参加者認証、録画管理、動画変換、視聴ページです。私なら、配信・認証・録画・変換の4つを責務ごとに分けます。

分ける理由は、一般に次のとおりです。

- 配信は低遅延が命で、負荷の山が配信時間帯に集中する
- 認証は配信が止まっていても動く必要がある
- 録画と変換は重く、リアルタイム性が不要なので非同期にできる
- 変更の理由が違うものを同じ場所に置くと、修正の影響範囲が広がる

以下は、各部分を最小限にしたサンプルです。実案件のコードではなく、考え方を示すための仮の例です。

### 参加者認証：署名付きトークンをシグナリングで検証する

簡単な参加手続きの一案として、会員管理側が発行した短寿命のトークンをURLに載せ、シグナリングのWebSocketで検証する方法があります。参加者はURLを開くだけで済みます。`ws` は npm パッケージです。

```js:signaling.js
import { WebSocketServer } from "ws";
import { createHmac, timingSafeEqual } from "node:crypto";

const SECRET = process.env.JOIN_TOKEN_SECRET;

// token = base64url(payload) + "." + base64url(hmac)
function verifyToken(token) {
  const [body, sig] = String(token).split(".");
  if (!body || !sig) return null;
  const expected = createHmac("sha256", SECRET).update(body).digest();
  const actual = Buffer.from(sig, "base64url");
  if (actual.length !== expected.length) return null;
  if (!timingSafeEqual(actual, expected)) return null;
  const payload = JSON.parse(Buffer.from(body, "base64url").toString());
  if (payload.exp * 1000 < Date.now()) return null;
  return payload; // { room, userId, role, exp }
}

const wss = new WebSocketServer({ port: 8080 });

wss.on("connection", (ws, req) => {
  const url = new URL(req.url, "http://localhost");
  const user = verifyToken(url.searchParams.get("token"));
  if (!user) {
    ws.close(1008, "unauthorized");
    return;
  }
  ws.user = user;
  ws.on("message", (data) => {
    // ここで同じ room の相手に SDP / ICE candidate を中継する
  });
});
```

ポイントは3つです。

- 比較には `timingSafeEqual` を使い、長さが違う場合は先に弾く
- 有効期限 `exp` を必ず検証する
- 検証に失敗したら、シグナリングの接続自体を閉じる

実運用では、トークンをクエリに載せるとログに残りやすい点に注意が必要です。私なら、アクセスログ側でマスクするか、接続直後の最初のメッセージで渡す方式にします。

### 配信：回線が弱い端末を前提に、送信ビットレートを抑える

配信側では、送信ビットレートの上限を明示しておくと、回線が細い環境で映像が崩れにくくなります。`RTCRtpSender.setParameters` で設定できます。

```js:publisher.js
const pc = new RTCPeerConnection({
  iceServers: [{ urls: "stun:stun.example.com:3478" }],
});

const stream = await navigator.mediaDevices.getUserMedia({
  video: { width: { ideal: 1280 }, height: { ideal: 720 }, frameRate: { ideal: 24 } },
  audio: true,
});
stream.getTracks().forEach((t) => pc.addTrack(t, stream));

const videoSender = pc.getSenders().find((s) => s.track?.kind === "video");
const params = videoSender.getParameters();
if (!params.encodings || params.encodings.length === 0) {
  params.encodings = [{}];
}
params.encodings[0].maxBitrate = 1_500_000; // 1.5 Mbps
await videoSender.setParameters(params);
```

`ideal` を使うと、端末が対応しない解像度でも失敗せず近い値に落ちます。`exact` は端末によってエラーになるため、複数端末を相手にするなら避けるのが無難です。数値は一例です。実際は対象の回線で測って決めてください。

TURNサーバーも、企業や学校のネットワークでは必要になることがあります。STUNだけで済む前提で作ると、本番で接続できない参加者が出ます。

### 録画管理と動画変換：重い処理は非同期のジョブに逃がす

録画ファイルは、配信と別のジョブで変換します。FFmpegでの変換の一例です。

```bash
ffmpeg -i input.webm \
  -c:v libx264 -preset veryfast -crf 23 \
  -c:a aac -b:a 128k \
  -movflags +faststart \
  output.mp4
```

- `libx264` と `aac` は、多くの端末で再生できる組み合わせである
- `-crf` は小さいほど高画質で、容量も増える
- `+faststart` は、再生開始までの待ちを短くするためメタデータを先頭に置く

変換は、キューに積んでワーカーで処理する形が扱いやすいです。録画のメタ情報（部屋、日時、状態）をMySQLなどで管理し、状態を「録画中、変換待ち、変換中、公開可」のように持たせます。すると、配信担当が手でファイルを探して変換する作業をなくせます。

## 複数端末での動作検証で確認したこと

この案件では、複数端末で動作を検証しました。検証の個別の結果は割愛しますが、同じ課題に取り組むなら、私は次の観点で確認します。

- OSとブラウザの組み合わせごとに、配信と視聴が成立するか
- カメラ・マイクの許可ダイアログで、利用者が迷わないか
- 回線を意図的に絞った状態で、映像と音声のどちらが先に劣化するか
- 接続が切れたときに、再接続で元の部屋へ戻れるか
- 録画ファイルが変換でき、音ずれなく再生できるか

回線の絞り込みは、ブラウザの開発者ツールのネットワーク制限などで手軽に試せます。ただし、WebRTCの通信にはそのまま効かないことがあるため、OS側の帯域制限ツールを併用するのが確実です。

音声は、映像より優先して守るのが一般的です。授業や研修では、映像が粗くても内容は伝わりますが、音が途切れると成立しません。

## 結果：配信準備から参加者管理までの運営作業時間を約50%削減

結果として、配信準備から参加者管理までの運営作業時間を約50%削減しました。

削減の中身について私が言えるのは、認証・録画管理・動画変換を仕組みに寄せる設計が、手作業を減らす方向に働くという一般論までです。個別の作業ごとの内訳は、ここでは示しません。

## 同じ課題に直面したら最初にやること

私なら、コードを書く前に次の順で進めます。

1. 運営の手作業を書き出し、時間のかかるものに印を付ける
2. 参加者に求める操作を最小にする（URLを開くだけ、を出発点にする）
3. 配信・認証・録画・変換を、責務ごとに分けて設計する
4. 重い処理は非同期ジョブにし、状態をDBで見えるようにする
5. 対象の端末と回線の組み合わせを決め、早い段階から実機で検証する
6. 運営向けに、ログと状態を見られる画面を用意する

### よくある落とし穴

- STUNだけで本番に出し、閉域に近いネットワークで繋がらない
- 認証トークンの有効期限がなく、URLが共有されて誰でも入れる
- 録画の変換を配信と同じサーバーで同時に走らせ、配信が重くなる
- 検証を開発機のみで済ませ、古い端末で初めて不具合に気づく
- 画質を上げすぎて、弱い回線の参加者が音声も聞こえなくなる
